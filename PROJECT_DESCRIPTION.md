# APIDeliveryCRM - Описание проекта

## Общая информация
**Название проекта:** APIDeliveryCRM  
**Тип проекта:** ASP.NET Core 8.0 Web API (SaaS Multi-Tenant)  
**База данных:** PostgreSQL (через Entity Framework Core)  
**Аутентификация:** JWT Bearer Token  
**Архитектура:** Multi-Tenant SaaS (Software as a Service)

## Стек технологий

### Backend
- **ASP.NET Core 8.0** - Веб-фреймворк для создания REST API
- **C#** - Язык программирования
- **Entity Framework Core** - ORM для работы с базой данных
- **PostgreSQL** - Реляционная база данных
- **JWT Bearer Token** - Аутентификация и авторизация
- **SignalR** - Реальное время для чата и уведомлений

### Асинхронная обработка и очереди
- **Apache Kafka** - Система обмена сообщениями для асинхронной обработки событий
  - Используется для децентрализации операций (уведомления, логирование, email)
  - Позволяет улучшить производительность API за счет асинхронной обработки
  - Поддержка Azure Event Hubs (Kafka-совместимый сервис)

### Облачные сервисы Azure
- **Azure Blob Storage** - Хранилище файлов (аватары, отчеты, вложения)
  - Гибридная система: автоматическое переключение между локальным хранилищем (wwwroot) и Azure Blob Storage
  - Масштабируемое хранилище для SaaS-приложения
- **Azure App Service** - Платформа для размещения веб-приложения
- **Azure Database for PostgreSQL** - Управляемая база данных PostgreSQL
- **Azure Event Hubs** - Kafka-совместимый сервис для обработки событий
- **Azure Application Insights** - Мониторинг производительности и диагностика
- **Azure Key Vault** - Безопасное хранение секретов и ключей
- **Azure SignalR Service** - Масштабируемый сервис для SignalR

### Кэширование и производительность
- **Redis** - In-memory хранилище данных для кэширования
  - Кэширование справочников (типы заказов, статусы, способы оплаты)
  - Кэширование геолокации курьеров в реальном времени
  - Rate limiting для защиты API от перегрузки
  - Pub/Sub для масштабирования SignalR (Azure SignalR Service использует Redis)
  - Кэширование списков заказов и профилей пользователей
  - Сессии для веб-приложений (если потребуется)
  - **Azure Cache for Redis** - Управляемый Redis в Azure

### Клиентские приложения

#### Архитектура клиентских приложений

Проект использует **гибридный подход** для клиентских приложений, учитывая различные потребности ролей:

**Роли и их требования:**
- **Курьер** - Мобильное приложение (iOS/Android) с геолокацией, офлайн-режимом, push-уведомлениями
- **Менеджер** - Десктопное приложение (Windows/macOS) или веб-интерфейс для управления заказами, аналитики
- **Логист** - Десктопное приложение (Windows/macOS) или веб-интерфейс для планирования маршрутов, оптимизации доставки

#### Связка Blazor + Flutter: SignalR и общая карта (OpenStreetMap)

**1. Связь по SignalR — да, оба клиента подключаются к одному хабу.**

- **Backend:** уже есть SignalR (например, `ChatHub` по адресу `/chatHub`). Один и тот же хаб может обслуживать и Blazor, и Flutter.
- **Blazor:** пакет `Microsoft.AspNetCore.SignalR.Client`. Подключение к `https://your-api/chatHub`, вызов методов хаба и подписка на события (`OnAsync("ReceiveMessage", ...)`). Работает в Blazor Server и Blazor WebAssembly.
- **Flutter:** пакет `signalr_netcore` (или `signalr_core`) из pub.dev. Подключение к тому же URL `/chatHub`, те же методы (`JoinRoom`, `SendMessage` и т.д.) и те же события. Протокол SignalR один и тот же, сервер не различает, кто подключён — Blazor или Flutter.

Для геолокации курьеров в реальном времени можно добавить отдельный хаб, например `MapHub`, куда Flutter (курьер) шлёт координаты, а Blazor (менеджер/логист) подписывается на обновления и отображает маркеры на карте. Оба клиента подключаются к одному и тому же `MapHub`.

**2. Одна и та же карта (кастом на базе OpenStreetMap) в Blazor и во Flutter — да.**

Идея: в обоих приложениях использовать одни и те же тайлы или один и тот же стиль карты (например, свой сервер тайлов или стиль в духе OSM).

- **Blazor (веб):** карта через **Leaflet** (JavaScript) и интероп с Blazor (например, `BlazorLeaflet`, `JsInterop` с Leaflet или обёртка вручную). Подложка — тайлы OpenStreetMap или кастомный URL, например:
  - стандартные OSM: `https://tile.openstreetmap.org/{z}/{x}/{y}.png`
  - кастомный тайл-сервер: `https://your-tileserver/{z}/{x}/{y}.png`
- **Flutter:** пакет **`flutter_map`** — аналог Leaflet для Flutter. Поддержка тайлов по URL из коробки. Задаётся тот же URL тайлов, например:
  - `TileLayer(urlTemplate: 'https://tile.openstreetmap.org/{z}/{x}/{y}.png', ...)` или ваш кастомный URL.

Если «кастомка» — это свой стиль OSM (свой тайл-сервер, например на базе OpenStreetMap data + Mapbox Studio / MapTiler / self-hosted), то в обоих клиентах указываете один и тот же базовый URL тайлов (или один стиль). Тогда карта визуально и по данным будет одной и той же в Blazor и во Flutter.

**Пакеты и ссылки:**

| Задача | Blazor | Flutter |
|--------|--------|---------|
| SignalR клиент | `Microsoft.AspNetCore.SignalR.Client` | `signalr_netcore` (pub.dev) |
| Карта (OSM/кастом) | Leaflet + JS Interop или BlazorLeaflet; тайлы OSM или свой URL | `flutter_map` + `latlong2`; тот же URL тайлов |

**Итог:** Blazor и Flutter можно связать по SignalR (один хаб на backend, два типа клиентов) и использовать одну и ту же карту на базе OpenStreetMap или кастомного тайл-сервера, задав в обоих приложениях один и тот же URL тайлов (или один стиль).

#### .NET MAUI (Multi-platform App UI)
- **Назначение:** Мобильное приложение для курьеров (iOS/Android)
- **Единая кодовая база** для iOS и Android
- **Нативные производительность и UI**
- **Поддержка нативных API платформ** (геолокация, камера, push-уведомления)

### Веб-технологии для менеджеров и логистов
- **Blazor Server** или **Blazor WebAssembly** - Веб-приложение на C#
  - Единая кодовая база с API (C# и .NET)
  - Кроссплатформенность (Windows, macOS, Linux через браузер)
  - Быстрое развертывание без установки
  - SignalR для реального времени (чат, уведомления)
  - Интеграция с Azure для масштабирования

### Мобильные технологии для MAUI (курьеры)
- **SQLite** - Локальная база данных для офлайн-режима
  - Кэширование данных при отсутствии интернета
  - Очередь действий для синхронизации при восстановлении связи
  - Быстрый доступ к часто используемым данным
  
- **Push Notifications**
  - **Firebase Cloud Messaging (FCM)** - Для Android
  - **Apple Push Notification Service (APNs)** - Для iOS
  - **Azure Notification Hubs** - Унифицированный сервис для всех платформ
  - Уведомления о новых заказах, изменениях статуса, сообщениях в чате

- **Геолокация и карты**
  - **Google Maps API** / **Azure Maps** / **Яндекс.Карты** / **Mapbox** - Отображение карт и маршрутов
  - **Background Location Tracking** - Отслеживание местоположения курьера в фоне
  - **Geofencing** - Уведомления при входе/выходе из зон доставки
  - **Route Optimization** - Оптимизация маршрутов доставки

- **Дополнительные возможности**
  - **QR Code Scanning** - Сканирование QR-кодов при доставке для подтверждения
  - **Camera/Photo Capture** - Фотографии при доставке, повреждениях упаковки
  - **Biometric Authentication** - Face ID / Touch ID для быстрого входа
  - **Offline Queue** - Очередь действий для выполнения при восстановлении связи
  - **Background Services** - Фоновые задачи для обновления геолокации, синхронизации данных

#### Интеграция с REST API
```dart
// Пример HTTP клиента
class ApiService {
  final Dio _dio = Dio(BaseOptions(
    baseUrl: 'https://api.deliverycrm.com',
    headers: {'Content-Type': 'application/json'},
  ));

  Future<List<Order>> getOrders() async {
    final response = await _dio.get('/api/Orders');
    return (response.data as List)
        .map((json) => Order.fromJson(json))
        .toList();
  }
}
```

### Наиболее подходящий стек для проекта Delivery CRM

С учётом архитектуры (Multi-Tenant SaaS), ролей (клиент, курьер, менеджер, логист) и уже реализованного backend (ASP.NET Core, PostgreSQL, SignalR, JWT) оптимальным является следующий стек:

| Слой | Технология | Обоснование |
|------|------------|-------------|
| **Backend** | ASP.NET Core 8, C#, EF Core, PostgreSQL | Уже реализован; единый язык с клиентами при выборе .NET-фронтов. |
| **Мобильное приложение (курьер)** | .NET MAUI 8 | Геолокация, офлайн, push, камера/QR; один стек с API и веб-панелью; проще обосновать в дипломе и поддерживать. |
| **Веб-приложение (менеджер, логист)** | Blazor Server или WebAssembly | Десктопный сценарий, дашборды, таблицы, чат; C# и общие DTO с API; SignalR из коробки. |
| **База данных** | PostgreSQL | Уже используется; надёжность, JSON/PostGIS при необходимости. |
| **Реальное время** | SignalR + (опционально) Azure SignalR | Чат и уведомления уже завязаны на SignalR. |
| **Файлы и кэш** | Azure Blob / локальный wwwroot; Redis при росте нагрузки | Соответствует текущей реализации и планам масштабирования. |
| **Очереди событий** | Kafka / Azure Event Hubs | Для асинхронных сценариев (уведомления, логи, рассылки). |

**Итог:** наиболее подходящий вариант — **Backend (ASP.NET Core + PostgreSQL + SignalR) + MAUI (курьер) + Blazor (менеджер/логист)**. Единый C#/.NET-стек, переиспользование моделей и логики, одна команда, проще диплом и поддержка. Flutter для курьера — разумная альтернатива только при приоритете «премиального» UI и наличии отдельного разработчика на Dart.

### Нужно ли делать приложение для клиента в SaaS?

В SaaS-модели **тенант** — это компания (служба доставки), которая пользуется системой. **Клиент (роль «Клиент»)** — это заказчик доставки, то есть контрагент тенанта (физлицо или организация, для кого делается доставка).

- **Роль «Клиент» в системе нужна всегда:** в БД должны быть пользователи с ролью «Клиент», профили (ClientProfile), привязка заказов к клиенту, адреса, чаты и т.д. Иначе нельзя однозначно указать, для кого заказ и с кем общаться.
- **Отдельное клиентское приложение (портал/приложение для клиента) — не обязательно.** Это продуктовая, а не техническая необходимость.

**Два варианта продукта:**

| Подход | Описание | Нужно ли приложение для клиента |
|--------|----------|----------------------------------|
| **B2B без self-service** | Заказы создают менеджеры/операторы от имени клиента. Клиент — запись в системе (контакт, адреса, история). Уведомления клиенту — по email/SMS или ссылка «отследить заказ» (read-only). | **Нет.** Достаточно API + Blazor для менеджера/логиста/курьера. Клиент может вообще не иметь логина. |
| **B2B с self-service** | Клиенты сами регистрируются, создают заказы, смотрят историю, общаются в чате, отслеживают доставку. | **Да.** Нужен клиентский фронт: веб-портал (например, Blazor или SPA) и/или мобильное приложение. |

**Рекомендация для дипломного/корпоративного SaaS:**

- **Делать отдельное приложение для клиента не обязательно.** Типичная схема: менеджер создаёт заказ в Blazor, выбирает или создаёт клиента (ClientProfile + User с ролью «Клиент» при необходимости), назначает курьера; клиент получает SMS/email со ссылкой на отслеживание (если реализовать одну страницу «трек по коду») или просто уведомления. Чат с клиентом ведёт менеджер/курьер из своей панели.
- **Стек тогда:** API + MAUI (курьер) + Blazor (менеджер, логист). Клиент остаётся ролью в данных и в API (регистрация, профиль, заказы, чат — для будущего self-service или для работы оператора от имени клиента), но **отдельного клиентского приложения не делаем**.
- Если позже понадобится self-service для клиентов — можно добавить отдельный Blazor-проект «клиентский портал» или раздел в том же Blazor с другим layout и правами доступа.

**Итог:** для SaaS delivery CRM **роль «Клиент» в модели и в API нужна**; **отдельное приложение для клиента — нет**, если продукт строится как B2B без клиентского self-service. Для диплома и типичного корпоративного сценария достаточно API + MAUI + Blazor для курьера и менеджера/логиста.

### Функционал пользователей системы (максимальный)

Ниже описан **полный целевой функционал по ролям**: уже реализованный в API и потенциальный «на максимум» для каждой роли. В текущей реализации в системе явно выделены роли: **Клиент**, **Курьер**, **Менеджер**; **Логист** может быть отдельной ролью (отдельная запись в таблице Roles) или подвидом менеджера с расширенными правами.

---

#### 1. Клиент (Client)

**Назначение:** заказчик доставки; создаёт заказы, управляет профилем и адресами, общается с менеджером/курьером, смотрит историю и отзывы.

**Уже реализовано в API:**
- Регистрация (POST /api/Users/RegisterClient).
- Вход (POST /api/Users/Login) — получение JWT.
- Получение/обновление профиля (GET/PUT /api/Clients/{id}), обновление предпочтительного способа оплаты и адреса по умолчанию.
- Просмотр своих заказов (GET /api/Clients/{id}/orders).
- Управление адресами (через модель Address и связь с User).
- Загрузка/обновление/получение аватара (POST/PUT /api/Files/avatar, GET /api/Files/avatar/{userId}).
- Чаты: список комнат, вход/выход, отправка/получение сообщений, пометка прочитанных, редактирование/удаление своих сообщений (ChatController).
- Уведомления: список, пометка прочитанным (GET /api/Notifications/user/{userId}, POST /api/Notifications/{id}/read).
- Тема интерфейса (GET/POST /api/Theme/{userId}).
- Отзывы: добавление, просмотр по пользователю и по заказу, редактирование (ReviewsController).
- Обновление ФИО (PUT /api/Users/{id}).

**Функционал «на максимум» (целевой):**
- Создание заказа с выбором адресов, типа заказа, способа оплаты, габаритов и т.д. (частично через CreateOrderRequest; расширить: выбор адреса из своих, расчёт стоимости, слоты доставки).
- Полный жизненный цикл заказа: черновик → подтверждён → в работе → у курьера → доставлен/отменён; просмотр статуса и истории в реальном времени (SignalR).
- Кабинет клиента: список заказов с фильтрами (дата, статус), поиск по номеру, экспорт в Excel/PDF.
- Управление адресами: CRUD адресов доставки/забора, карта с выбором точки, избранные адреса.
- Способы оплаты: привязка карт/кошельков (если предусмотрено продуктом), выбор способа по умолчанию.
- Чаты: чат по заказу с менеджером и курьером, вложения (фото/документы), индикатор «печатает», push при новом сообщении.
- Уведомления: настройка типов (email, push, in-app), история уведомлений.
- Отзывы и рейтинг: отзыв по доставке, рейтинг курьера/сервиса, ответы на отзывы (если нужно).
- Поддержка: тикет/обратная связь, прикрепление файлов.
- Документы: скачивание актов, накладных, чеков по заказам (если реализовать генерацию на backend).
- Локализация и доступность: смена языка, темы (light/dark), размер шрифта (если делается веб/мобильное приложение для клиента).

#### 2. Курьер (Courier)

**Назначение:** выполнение доставок: смена, заказы, маршрут, геолокация, подтверждение доставки, отчёты и чат.

**Уже реализовано в API:**
- Регистрация (POST /api/Users/RegisterCourier) с категорией ТС и графиком работы.
- Вход (POST /api/Users/Login).
- Профиль курьера (GET /api/Couriers/{id}) с рейтингом, статусом, количеством доставок.
- Активные заказы (GET /api/Couriers/{id}/orders).
- Обновление геолокации и онлайн-статуса (POST /api/Couriers/{id}/location, POST /api/Couriers/{id}/online).
- Смены: начало/конец смены (POST /api/Couriers/{id}/shift/start, POST /api/Couriers/shift/{shiftId}/end).
- Чаты, уведомления, аватар, тема — те же endpoints, что и у других ролей.
- Загрузка отчётов (POST /api/Files/report), получение отчёта (GET /api/Files/report/{reportId}).

**Функционал «на максимум» (целевой):**
- Смены: просмотр графика смен, история смен, учёт времени и пробега (при наличии VehicleAssignment); уведомления о начале смены.
- Заказы: список назначенных заказов с приоритетом и сроками; приём/отказ заказа; маршрут на день с оптимизацией порядка (если внедряется логистика).
- Навигация и карта: отображение точек забора/доставки, построение маршрута (интеграция с картами), трекинг в реальном времени для диспетчера.
- Подтверждение этапов: «забрал груз» (фото/подпись), «на месте доставки», «доставлено» (подпись получателя, фото, QR/штрихкод при необходимости).
- Офлайн-режим: кэш заказов и маршрутов в SQLite, очередь действий при отсутствии сети, синхронизация при появлении связи.
- Push-уведомления: новый заказ, изменение заказа/отмена, сообщение в чате, напоминания о смене.
- Отчёты: расходы (топливо, парковка), фото повреждений, служебные отчёты с привязкой к заказу/смене; статусы отчётов (модель ReportStatus).
- Транспорт: привязка ТС (VehicleAssignment), фиксация пробега в начале/конце смены.
- Рейтинг и статистика: личная статистика доставок, рейтинг, достижения/бейджи (если заложить в продукт).
- Безопасность: биометрия для входа, защищённое хранение токена.
- Чаты: быстрый чат с клиентом/менеджером по заказу, голосовые сообщения (при реализации на клиенте).

#### 3. Менеджер (Manager)

**Назначение:** управление заказами, клиентами и курьерами; работа с чатами и уведомлениями; базовая отчётность.

**Уже реализовано в API:**
- Регистрация (POST /api/Users/RegisterManager), вход (POST /api/Users/Login).
- Список курьеров и менеджеров (GET /api/Users/GetAllCourier, GET /api/Users/GetAllManagers).
- Заказы: создание (POST /api/Orders с CreateOrderRequest), просмотр по id/клиенту/курьеру (GET /api/Orders/{id}, .../client/{clientId}, .../courier/{courierId}), обновление (PUT), смена статуса (POST /api/Orders/{id}/status), назначение курьера (POST /api/Orders/{id}/assign).
- Профили клиентов и курьеров (GET /api/Clients/{id}, GET /api/Couriers/{id}).
- Чаты, уведомления, аватар, тема, отзывы — общие endpoints.
- Загрузка и получение отчётов (FilesController report).
- Просмотр пользователей (GET /api/Users/getById, getAllUsers), обновление пользователя (PUT /api/Users/{id}).

**Функционал «на максимум» (целевой):**
- Дашборд: сводка по заказам (в работе, на сегодня, просроченные), активные курьеры, ключевые KPI (доставки за день/неделю, среднее время доставки).
- Управление заказами: полный CRUD, массовые операции (смена статуса, переназначение курьера), фильтры (дата, статус, клиент, курьер), поиск по номеру/клиенту.
- Управление клиентами: список клиентов, карточка клиента (профиль, история заказов, отзывы, чаты), блокировка/активация, примечания.
- Управление курьерами: список с онлайн-статусом и геолокацией, смены и занятость, назначение заказов, просмотр рейтинга и статистики.
- Календарь смен: просмотр и редактирование смен курьеров (при расширении Shift API).
- Чаты: общие чаты по заказам, переключение между чатами, уведомления о новых сообщениях.
- Уведомления: централизованный список, фильтр по типу/заказу, массовая пометка прочитанными.
- Отчёты: создание и загрузка отчётов (по типам и периодам), просмотр списка отчётов и их статусов (ReportStatus), выгрузка отчётов.
- Справочники: типы заказов, статусы заказов, статусы курьеров, способы оплаты, типы упаковок и т.д. (при наличии соответствующих API).
- Аудит: просмотр логов изменений по заказам/пользователям (AuditLog при подключении к UI).
- Оповещения и эскалации: правила «если заказ просрочен — уведомить менеджера» (при реализации правил на backend).

#### 4. Логист (Logistician)

**Назначение:** планирование маршрутов, оптимизация загрузки курьеров, зоны и тайм-слоты доставки, аналитика по доставкам. В текущей модели может быть отдельная роль «Логист» (отдельная запись в Roles) или расширенные права у менеджера.

**Уже реализовано в API (общее с менеджером):**
- Те же endpoints заказов, курьеров, чатов, уведомлений; доступ к списку заказов и курьеров, назначение курьера.

**Функционал «на максимум» (целевой):**
- Планирование смен: распределение курьеров по сменам и зонам, учёт графика работы (ScheduleType) и категории ТС (VehicleCategory).
- Назначение заказов: массовое назначение по зоне/времени, автоматическое предложение курьера по близости и загрузке (при реализации алгоритма на backend).
- Маршруты: построение маршрутов на день для курьера, оптимизация порядка посещения точек (TSP-подобная логика или интеграция с внешним роутинг-API).
- Зоны доставки: задание зон, тайм-слоты, ограничение по весу/габаритам по зонам (при появлении соответствующих сущностей в БД).
- Мониторинг в реальном времени: карта с курьерами и заказами, прогресс доставок, опоздания и предупреждения.
- Аналитика: загрузка курьеров, среднее время доставки по зонам, использование транспорта, эффективность смен; графики и выгрузки (Excel/PDF).
- Отчёты: логистические отчёты (пробег, топливо при наличии данных), отчёты по зонам и тайм-слотам.
- Интеграции: импорт заказов из файлов, выгрузка для внешних систем (1С, WMS и т.д.) при необходимости.

## Kafka - Асинхронная обработка событий

### Назначение Kafka в проекте
Kafka используется для асинхронной обработки событий и децентрализации операций, что значительно улучшает производительность API.

### Основные сценарии использования:
1. **Уведомления** - Создание уведомлений асинхронно, без блокировки основного потока API
2. **Логирование** - Асинхронная запись логов событий
3. **Email-рассылки** - Отправка email уведомлений в фоновом режиме
4. **События заказов** - Публикация событий при изменении статуса заказа, назначении курьера
5. **Аналитика** - Сбор метрик и событий для аналитики

### Архитектура Kafka в проекте:
- **Producer** - Публикует события в топики Kafka
- **Consumer** - Фоновый сервис (Background Service) обрабатывает события из топиков
- **Topics** - Топики для различных типов событий:
  - `notifications` - События уведомлений
  - `orders` - События заказов
  - `logs` - События логирования
  - `emails` - События отправки email

### Преимущества:
- **Производительность** - API не блокируется на долгих операциях
- **Масштабируемость** - Легко добавить новых потребителей событий
- **Надежность** - События не теряются при сбоях
- **Гибкость** - Легко добавить новые обработчики событий

### Различие между Kafka и SignalR:
- **SignalR** - Для реального времени (server-to-client), когда нужно мгновенно обновить UI клиента
- **Kafka** - Для асинхронной обработки событий в фоне, когда не требуется мгновенная реакция клиента

## Redis - Кэширование и производительность

### Зачем нужен Redis в Delivery CRM?

Redis критически важен для производительности SaaS-приложения, особенно при работе с MAUI клиентами:

#### 1. Кэширование справочников
- **Типы заказов**, **статусы**, **способы оплаты**, **категории транспорта**
- Эти данные редко меняются, но часто запрашиваются
- Снижение нагрузки на PostgreSQL на 70-80%

#### 2. Кэширование геолокации курьеров
- Текущие координаты курьеров обновляются каждые 5-10 секунд
- Redis хранит актуальные позиции в реальном времени
- Быстрый поиск ближайших курьеров для назначения заказов

#### 3. Rate Limiting
- Защита API от DDoS и злоупотреблений
- Ограничение количества запросов с одного IP/пользователя
- Особенно важно для публичных API endpoints

#### 4. Масштабирование SignalR
- Azure SignalR Service использует Redis для координации между серверами
- При горизонтальном масштабировании все серверы видят одни и те же подключения

#### 5. Кэширование списков заказов
- Списки заказов клиента/курьера кэшируются на 1-5 минут
- Значительное снижение нагрузки на БД при частых обновлениях в MAUI приложении

#### 6. Сессии (если потребуется веб-версия)
- Хранение временных данных сессии
- Хотя используется JWT, Redis может хранить refresh tokens

### Когда Redis НЕ нужен:
- ❌ Для хранения постоянных данных (используйте PostgreSQL)
- ❌ Для сложных запросов и JOIN'ов (PostgreSQL лучше)
- ❌ Для транзакций (PostgreSQL с ACID)

### Когда Redis ОБЯЗАТЕЛЕН:
- ✅ Высокая нагрузка (1000+ запросов/сек)
- ✅ Несколько серверов API (горизонтальное масштабирование)
- ✅ Реальное время (геолокация, уведомления)
- ✅ MAUI приложения с частыми обновлениями UI

## 3.3 Проектирование программного обеспечения

Для начала работы над проектом была спроектирована архитектура базы данных в PostgreSQL с использованием Entity Framework Core. Проектирование базы данных играет фундаментальную роль в успешности и производительности REST API. В условиях высоких нагрузок и необходимости обеспечения целостности данных именно продуманная структура базы данных становится тем решающим фактором, который определяет стабильность работы системы. Разработчики буквально за несколько секунд оценивают качество API, проверяя его производительность и корректность возвращаемых данных. Если структура базы данных спроектирована неправильно, велика вероятность возникновения проблем с производительностью, целостностью данных и масштабируемостью системы.

Важность проектирования базы данных выходит далеко за рамки простого хранения информации. Правильно спроектированная схема данных значительно снижает нагрузку на сервер, позволяя эффективно выполнять запросы и обеспечивать быстрый отклик API. Когда связи между таблицами настроены корректно, а индексы созданы для часто используемых полей, взаимодействие с базой данных становится оптимальным. Это напрямую влияет на скорость обработки запросов и на способность системы обрабатывать большое количество одновременных подключений (Рисунок 3.1).

Рисунок 3.1 Схема базы данных (ER-диаграмма)

PostgreSQL представляет собой мощную реляционную систему управления базами данных с открытым исходным кодом, которая обеспечивает надежность, производительность и расширяемость. Одним из ключевых преимуществ PostgreSQL является поддержка сложных типов данных, транзакций ACID, внешних ключей и ограничений целостности, что критически важно для системы управления доставкой, где необходимо гарантировать согласованность данных о заказах, пользователях и платежах.

Entity Framework Core значительно упрощает работу с базой данных, предоставляя объектно-реляционное отображение (ORM), которое позволяет работать с данными как с объектами C#, а не напрямую с SQL-запросами. Это ускоряет разработку, снижает вероятность ошибок и обеспечивает типобезопасность. Миграции Entity Framework Core позволяют версионировать изменения схемы базы данных и применять их последовательно, что критически важно при работе в команде и развертывании на различных окружениях.

Такой подход обеспечивает создание масштабируемого и поддерживаемого API, которое может работать на различных платформах (Windows, Linux, macOS) и интегрироваться с различными клиентскими приложениями.

Средой разработки для создания REST API выбрана Visual Studio 2022 — современная интегрированная среда разработки (IDE) с широкими возможностями для работы с .NET приложениями. Использование Visual Studio значительно ускоряет процесс разработки, позволяет оперативно находить и исправлять ошибки благодаря встроенному отладчику, IntelliSense для автодополнения кода и интеграции с системой управления версиями Git. IDE идеально подходит для работы с ASP.NET Core, предоставляя все необходимые инструменты для создания, тестирования и развертывания API в одном месте.

Архитектура приложения построена по принципу трехуровневой архитектуры (three-tier architecture), которая разделяет приложение на три основных слоя:

1. **Слой представления (Presentation Layer)** – контроллеры (Controllers), которые обрабатывают HTTP-запросы и возвращают ответы;
2. **Слой бизнес-логики (Business Logic Layer)** – сервисы (Services), которые содержат всю бизнес-логику приложения;
3. **Слой доступа к данным (Data Access Layer)** – контекст базы данных (ContextDB) и модели Entity Framework Core.

Такое разделение обеспечивает модульность, тестируемость и поддерживаемость кода, позволяя легко вносить изменения в один слой без влияния на другие (Рисунок 3.2).

Используется `ReferenceHandler.IgnoreCycles` в настройках JSON сериализации и атрибут `[JsonIgnore]` на навигационных свойствах для предотвращения ошибок сериализации.

## 3.5 Тестирование ПО

Тестирование по стратегии чёрного ящика, часто называемое функциональным тестированием — это методика, изучающая функциональность ПО без необходимости знания внутренней структуры кода. Она может применяться на всех уровнях тестирования ПО, но в основном используется на высоких уровнях. Тестирование по стратегии чёрного ящика — это процесс тестирования системы и её поведения вне зависимости от её внутренней структуры, архитектуры и реализации.

Для тестирования REST API используется Swagger UI – инструмент, который автоматически генерирует интерактивную документацию API на основе атрибутов контроллеров и моделей. Swagger UI позволяет отправлять HTTP-запросы к API, просматривать структуру запросов и ответов, а также проверять работу всех endpoints без необходимости написания дополнительного клиентского кода.

Для того, чтобы протестировать загрузку аватара пользователя, необходимо выполнить следующие шаги: авторизоваться в системе через endpoint POST /api/Users/Login, получив JWT токен; использовать полученный токен для аутентификации последующих запросов; отправить POST запрос к endpoint /api/Files/avatar с параметром userId и прикрепить файл изображения (например, JPG или PNG) через форму multipart/form-data в Swagger UI (Рисунок 3.8).
