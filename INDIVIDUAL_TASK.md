# ИНДИВИДУАЛЬНОЕ ЗАДАНИЕ НА ТЕМУ «Разработка REST API для системы управления доставкой (Delivery CRM)»

## Технологические процессы

В ходе прохождения производственной практики изучены следующие технологические процессы:

− сбор требований и анализ предметной области. Определение целевой аудитории (клиенты, курьеры, менеджеры) и основных сценариев использования приложения для управления доставкой;

− проектирование архитектуры REST API. Создание структуры базы данных, определение моделей данных и связей между сущностями;

− разработка архитектуры приложения на C#. Выбор паттернов проектирования (трехуровневая архитектура: Controllers, Services, Interfaces);

− настройка среды разработки. Выбор технологического стека (ASP.NET Core 8.0, Entity Framework Core, PostgreSQL, JWT Bearer Token, SignalR);

− реализация системы аутентификации и авторизации пользователей с использованием JWT токенов;

− разработка бизнес-логики для управления заказами, пользователями, чатом в реальном времени и уведомлениями;

− тестирование API методом черного ящика через Swagger UI;

− оптимизация запросов к базе данных и обработка циклических ссылок в JSON.

Результатом выполнения производственной практики является полностью функциональное REST API для системы управления доставкой, готовое к интеграции с клиентскими приложениями (мобильными и веб), с реализованными бизнес-процессами согласно техническому заданию.

## 1 ИНДИВИДУАЛЬНОЕ ЗАДАНИЕ

### 3.1 Формулировка индивидуального задания

Разработать REST API для системы управления доставкой «Delivery CRM», обеспечивающее централизованное управление процессами доставки и взаимодействие между клиентами, курьерами и менеджерами. Система должна включать систему авторизации пользователей с различными ролями (клиент, курьер, менеджер), позволяющую входить в аккаунт через электронную почту и пароль с использованием JWT токенов для безопасной аутентификации.

После входа пользователи смогут выполнять действия в соответствии со своей ролью: клиенты могут создавать заказы на доставку с указанием адресов забора и доставки, типов упаковки и способов оплаты; курьеры могут просматривать назначенные заказы, обновлять свое местоположение и статус работы; менеджеры могут управлять заказами, назначать курьеров, отслеживать статистику и формировать отчеты.

Важным функционалом является система чата в реальном времени на основе SignalR, позволяющая участникам заказа общаться между собой, отправлять сообщения и получать уведомления о новых сообщениях. Дополнительно система должна обеспечивать управление профилями пользователей с возможностью загрузки аватаров, настройки темы интерфейса (светлая/темная), а также систему уведомлений для информирования пользователей о важных событиях, таких как изменение статуса заказа или получение нового сообщения в чате.

### 3.2 Анализ предметной области

Предметная область, охватываемая разработкой REST API «Delivery CRM», связана с автоматизацией процессов управления службой доставки и координацией взаимодействия между различными участниками системы доставки. Основная цель системы заключается в централизации управления заказами, оптимизации маршрутов курьеров, обеспечении прозрачности процесса доставки для клиентов и предоставлении менеджерам инструментов для эффективного управления бизнес-процессами.

В центре внимания находятся три основные группы пользователей системы. Клиенты являются инициаторами процесса доставки и основными получателями услуг. В системе хранится информация о клиентах, включая их личные данные (фамилия, имя, отчество), контактные данные, адреса доставки, предпочтения по способам оплаты и история заказов. Это позволяет компании персонализировать услуги, анализировать поведение клиентов и улучшать качество обслуживания.

Курьеры представляют собой ключевой элемент системы доставки. В базе данных фиксируется информация о каждом курьере, включая данные о транспортном средстве (категория, модель, марка), водительские права, паспортные данные, график работы, текущий статус (на смене, свободен, занят), рейтинг и статистику выполненных доставок. Система отслеживает местоположение курьеров в реальном времени через координаты GPS, что позволяет оптимально распределять заказы и планировать маршруты.

Менеджеры осуществляют координацию работы службы доставки. Система предоставляет им доступ к управлению заказами, назначению курьеров, изменению статусов заказов, просмотру аналитики и формированию отчетов. Информация о менеджерах включает должность, отдел, контактные данные и дату найма.

Система управления заказами является центральным компонентом приложения. В базе данных фиксируются данные о каждом заказе, включая название, описание, номер заказа, тип заказа, статус выполнения, назначенного курьера, габариты и вес посылки, адреса забора и доставки, стоимость (предварительную и финальную), способ оплаты и статус оплаты. Учет статусов заказов (новый, в обработке, назначен курьеру, в пути, доставлен, отменен) помогает отслеживать процесс выполнения доставки на каждом этапе и информировать всех участников о текущем состоянии заказа.

Система чата в реальном времени обеспечивает коммуникацию между участниками заказа. Каждый заказ может иметь связанную чат-комнату, где клиент, курьер и менеджер могут обмениваться сообщениями, уточнять детали доставки и решать возникающие вопросы. Сообщения хранятся в базе данных с указанием отправителя, времени отправки, возможности редактирования и удаления.

Система уведомлений информирует пользователей о важных событиях: изменении статуса заказа, назначении курьера, получении нового сообщения в чате, изменении времени доставки. Уведомления классифицируются по типам и могут быть связаны с конкретным заказом.

Дополнительно система включает управление отчетами, которые могут формироваться менеджерами для анализа работы службы доставки. Отчеты имеют различные типы (ежедневные, еженедельные, месячные, пользовательские) и статусы обработки (ожидает, в обработке, готов, ошибка, отменен).

### 3.3 Проектирование программного обеспечения

Для начала работы над проектом была спроектирована архитектура базы данных в PostgreSQL с использованием Entity Framework Core. Проектирование базы данных играет фундаментальную роль в успешности и производительности REST API. В условиях высоких нагрузок и необходимости обеспечения целостности данных именно продуманная структура базы данных становится тем решающим фактором, который определяет стабильность работы системы. Разработчики буквально за несколько секунд оценивают качество API, проверяя его производительность и корректность возвращаемых данных. Если структура базы данных спроектирована неправильно, велика вероятность возникновения проблем с производительностью, целостностью данных и масштабируемостью системы.

Важность проектирования базы данных выходит далеко за рамки простого хранения информации. Правильно спроектированная схема данных значительно снижает нагрузку на сервер, позволяя эффективно выполнять запросы и обеспечивать быстрый отклик API. Когда связи между таблицами настроены корректно, а индексы созданы для часто используемых полей, взаимодействие с базой данных становится оптимальным. Это напрямую влияет на скорость обработки запросов и на способность системы обрабатывать большое количество одновременных подключений.

PostgreSQL представляет собой мощную реляционную систему управления базами данных с открытым исходным кодом, которая обеспечивает надежность, производительность и расширяемость. Одним из ключевых преимуществ PostgreSQL является поддержка сложных типов данных, транзакций ACID, внешних ключей и ограничений целостности, что критически важно для системы управления доставкой, где необходимо гарантировать согласованность данных о заказах, пользователях и платежах.

Entity Framework Core значительно упрощает работу с базой данных, предоставляя объектно-реляционное отображение (ORM), которое позволяет работать с данными как с объектами C#, а не напрямую с SQL-запросами. Это ускоряет разработку, снижает вероятность ошибок и обеспечивает типобезопасность. Миграции Entity Framework Core позволяют версионировать изменения схемы базы данных и применять их последовательно, что критически важно при работе в команде и развертывании на различных окружениях.

Основные таблицы базы данных:

1. **Users** (ID пользователя, Фамилия, Имя, Отчество, Дата создания, Активен, Тема интерфейса, ID роли);
2. **Logins** (ID логина, Email, Хешированный пароль, ID пользователя);
3. **Roles** (ID роли, Название роли);
4. **ClientProfiles** (ID профиля клиента, ID пользователя, Адрес по умолчанию, Рейтинг, ID предпочитаемого способа оплаты);
5. **CourierProfiles** (ID профиля курьера, ID пользователя, ID категории транспорта, Водительские права, Паспортные данные, ID графика работы, ID текущего статуса, Рейтинг, Всего доставок, Онлайн статус, Текущие координаты, Время последней активности);
6. **ManagerProfiles** (ID профиля менеджера, ID пользователя, Должность, Отдел, Данные паспорта, Телефон, Дата найма);
7. **Orders** (ID заказа, Название, Описание, Номер заказа, ID клиента, ID типа заказа, ID статуса, ID курьера, ID типа упаковки, Вес, Высота, Длина, Ширина, Предварительная стоимость, Финальная стоимость, Дата создания, Дата доставки, ID способа оплаты, Оплачен, ID адреса забора, ID адреса доставки);
8. **Addresses** (ID адреса, Улица, Дом, Квартира, Город, Регион, Почтовый индекс, Комментарий, Широта, Долгота, ID пользователя);
9. **ChatRooms** (ID чат-комнаты, Название, ID типа комнаты, ID заказа, Дата создания, Дата последнего сообщения);
10. **ChatMessages** (ID сообщения, ID чат-комнаты, ID отправителя, Текст сообщения, URL вложения, Дата отправки, Дата редактирования, Удалено);
11. **ChatParticipants** (ID участника, ID чат-комнаты, ID пользователя, Дата присоединения, Дата выхода, Активен, Дата последнего прочтения);
12. **Reports** (ID отчета, Название, Описание, Путь к файлу, Тип отчета, ID пользователя, ID статуса, Дата создания, Начало периода, Конец периода);
13. **Notifications** (ID уведомления, ID пользователя, ID типа уведомления, Заголовок, Сообщение, ID заказа, Прочитано, Дата отправки).

REST API разрабатывается на C# с использованием фреймворка ASP.NET Core 8.0, что позволяет обеспечить высокую производительность, кроссплатформенность и современные возможности разработки веб-приложений. Такой подход обеспечивает создание масштабируемого и поддерживаемого API, которое может работать на различных платформах (Windows, Linux, macOS) и интегрироваться с различными клиентскими приложениями.

Средой разработки для создания REST API выбрана Visual Studio 2022 – современная интегрированная среда разработки (IDE) с широкими возможностями для работы с .NET приложениями. Использование Visual Studio значительно ускоряет процесс разработки, позволяет оперативно находить и исправлять ошибки благодаря встроенному отладчику, IntelliSense для автодополнения кода и интеграции с системой управления версиями Git. IDE идеально подходит для работы с ASP.NET Core, предоставляя все необходимые инструменты для создания, тестирования и развертывания API в одном месте.

Архитектура приложения построена по принципу трехуровневой архитектуры (three-tier architecture), которая разделяет приложение на три основных слоя:

1. **Слой представления (Presentation Layer)** – контроллеры (Controllers), которые обрабатывают HTTP-запросы и возвращают ответы;
2. **Слой бизнес-логики (Business Logic Layer)** – сервисы (Services), которые содержат всю бизнес-логику приложения;
3. **Слой доступа к данным (Data Access Layer)** – контекст базы данных (ContextDB) и модели Entity Framework Core.

Такое разделение обеспечивает модульность, тестируемость и поддерживаемость кода, позволяя легко вносить изменения в один слой без влияния на другие.

### 3.4 Разработка ПО

Создание REST API — это структурированный и последовательный процесс, который начинается с настройки проекта в Visual Studio 2022. На этом первом этапе инициализируется новый проект ASP.NET Core Web API, выбирается для него осмысленное название, которое отражает суть и функциональное назначение будущего API. Грамотно организованная структура проекта закладывает основу для стабильной работы и удобного сопровождения кода.

Структура проекта организована следующим образом:
- **Controllers/** – содержит все API контроллеры, которые обрабатывают HTTP-запросы;
- **Services/** – содержит сервисы с бизнес-логикой;
- **Interfaces/** – содержит интерфейсы для сервисов, обеспечивая инверсию зависимостей;
- **Model/** – содержит модели данных Entity Framework Core;
- **ContextDb/** – содержит контекст базы данных;
- **Request/** – содержит DTO (Data Transfer Objects) для входящих запросов;
- **Migrations/** – содержит миграции базы данных;
- **Hubs/** – содержит SignalR хабы для реального времени.

После успешной настройки структуры проекта следующим ключевым этапом разработки становится создание моделей данных и настройка контекста базы данных. На этом этапе определяются все сущности системы (User, Order, ChatRoom и др.), их свойства, связи между ними и ограничения целостности. Entity Framework Core автоматически создает SQL-запросы для работы с базой данных на основе этих моделей, что значительно упрощает разработку и снижает вероятность ошибок.

В процессе разработки создается иерархия сервисов, где каждый сервис отвечает за определенную область функциональности: UserService для работы с пользователями, OrderService для управления заказами, ChatService для чата, NotificationService для уведомлений и т.д. Каждый сервис реализует соответствующий интерфейс, что позволяет легко тестировать код и заменять реализации при необходимости.

Для начала реализуется система аутентификации и авторизации. Создается UserService, который обрабатывает регистрацию пользователей (клиентов, курьеров, менеджеров) и вход в систему. При регистрации пароль хешируется с использованием SHA256 и сохраняется в базе данных. При успешном входе генерируется JWT токен, который содержит информацию о пользователе (ID, email, имя, роль) и используется для последующей аутентификации запросов.

Далее реализуется функционал управления заказами. OrderService предоставляет методы для создания заказов, получения списка заказов, обновления статусов и назначения курьеров. При создании заказа автоматически генерируется уникальный номер заказа, рассчитывается предварительная стоимость на основе типа заказа, габаритов и расстояния между адресами.

Следующим этапом реализуется система чата в реальном времени на основе SignalR. Создается ChatHub, который обеспечивает двустороннюю связь между сервером и клиентами. При отправке сообщения оно сохраняется в базе данных, отправляется всем участникам чат-комнаты через SignalR и создаются уведомления для участников, которые не в сети.

Реализуется система управления файлами (FileService) для загрузки аватаров пользователей и отчетов. Файлы сохраняются в папке wwwroot на сервере, а пути к файлам хранятся в базе данных. Настраивается поддержка статических файлов, чтобы клиенты могли получать доступ к загруженным файлам через HTTP-запросы.

Добавляется система уведомлений (NotificationService), которая позволяет отправлять уведомления пользователям о важных событиях: изменении статуса заказа, назначении курьера, получении нового сообщения. Уведомления классифицируются по типам и могут быть связаны с конкретным заказом.

Настраивается обработка циклических ссылок в JSON, так как модели Entity Framework Core содержат навигационные свойства, которые могут создавать циклические ссылки при сериализации. Используется ReferenceHandler.IgnoreCycles и атрибут [JsonIgnore] на навигационных свойствах для предотвращения ошибок сериализации.

Создание REST API представляет собой гармоничное сочетание технического мастерства и системного подхода. Этот процесс начинается с анализа требований, который постепенно обретает форму через тщательное проектирование базы данных и кропотливую реализацию бизнес-логики. Каждый этап разработки – от создания моделей до написания контроллеров – наполнен техническими решениями и архитектурными паттернами.

Архитектурная составляющая играет ключевую роль в создании успешного API. Разработчики работают над тем, чтобы код был не только функциональным, но и поддерживаемым, масштабируемым и тестируемым. Разделение на слои, использование интерфейсов, внедрение зависимостей через конструкторы – все это обеспечивает качество и надежность разрабатываемого решения.

### 3.5 Тестирование ПО

Тестирование по стратегии чёрного ящика, часто называемое функциональным тестированием — это методика, изучающая функциональность ПО без необходимости знания внутренней структуры кода. Она может применяться на всех уровнях тестирования ПО, но в основном используется на высоких уровнях. Тестирование по стратегии чёрного ящика — это процесс тестирования системы и её поведения вне зависимости от её внутренней структуры, архитектуры и реализации.

Для тестирования REST API используется Swagger UI – инструмент, который автоматически генерирует интерактивную документацию API на основе атрибутов контроллеров и моделей. Swagger UI позволяет отправлять HTTP-запросы к API, просматривать структуру запросов и ответов, а также проверять работу всех endpoints без необходимости написания дополнительного клиентского кода.

Для того, чтобы протестировать создание заказа, необходимо выполнить следующие шаги: авторизоваться в системе через endpoint POST /api/Users/Login, получив JWT токен; использовать полученный токен для аутентификации последующих запросов; отправить POST запрос к endpoint /api/Orders с телом запроса, содержащим данные заказа (название, описание, ID клиента, ID типа заказа, адреса забора и доставки, габариты и т.д.).

Если при отправке запроса заказ успешно создан и возвращен с присвоенным ID и номером заказа, значит тестирование прошло успешно. API должен вернуть статус код 200 (OK) и объект созданного заказа с заполненными полями, включая автоматически сгенерированный номер заказа и дату создания.
